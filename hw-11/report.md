# HW11 — Секционирование таблицы бронирований в PostgreSQL

## 1. Цель и окружение

**Цель:** проанализировать демонстрационную базу авиаперевозок Postgres Professional, выбрать стратегию секционирования, перенести существующие данные в секционированную структуру, проверить маршрутизацию строк, сравнить планы запросов и протестировать операции `INSERT`, `UPDATE`, `DELETE`.

- СУБД: PostgreSQL 17, контейнер Docker `hw09-postgres`.
- База данных: `demo` (демонстрационная база авиаперевозок Postgres Professional).
- Исходная таблица: `bookings.bookings`.
- Учебная секционированная копия: `hw11.bookings_part`.
- Исходная таблица и её внешние ключи не изменялись.

## 2. Анализ структуры и данных

Структура исходной таблицы:

```text
bookings.bookings
  book_ref     character(6)               NOT NULL  PRIMARY KEY
  book_date    timestamp with time zone    NOT NULL
  total_amount numeric(10,2)              NOT NULL
```

Таблица `tickets` ссылается на `bookings(book_ref)` внешним ключом `tickets_book_ref_fkey`. Поэтому для учебного эксперимента выбрано создание отдельной таблицы, а не замена оригинала: переход на секционированную таблицу потребовал бы дополнительного проектирования ключей и зависимостей.

Исходные данные:

| Показатель | Значение |
|---|---:|
| Число бронирований | 1 292 893 |
| Минимальная дата | `2025-09-01 00:00:06.265219+00` |
| Максимальная дата | `2025-11-30 23:59:28.616825+00` |

Распределение по месяцам (в UTC):

| Период | Строк |
|---|---:|
| Сентябрь 2025 | 448 064 |
| Октябрь 2025 | 434 159 |
| Ноябрь 2025 | 410 670 |
| **Итого** | **1 292 893** |

### Выбор метода

Применено **декларативное секционирование `RANGE (book_date)` по календарным месяцам**. Даты естественно образуют интервалы, а запросы за определённый месяц могут ограничиваться только относящейся к нему секцией (*partition pruning*). Дополнительно создана секция `DEFAULT` для дат вне заданных диапазонов. Границы указаны явно в UTC, чтобы исключить зависимость от локального часового пояса при определении месяцев.

Для копии задан `PRIMARY KEY (book_ref, book_date)`, так как PostgreSQL требует включать ключ секционирования в уникальное ограничение/PK родительской секционированной таблицы. **Отличие от исходного `PRIMARY KEY (book_ref)` существенно:** глобальная уникальность одного `book_ref` в новой схеме не обеспечивается; использовать её как прямую замену исходной таблице без переработки связей нельзя.

## 3. Создание секций и миграция

Создана таблица `hw11.bookings_part`, секционированная по диапазонам `book_date`:

| Секция | Границы (`FROM` включительно, `TO` исключительно) | Перенесено строк |
|---|---|---:|
| `hw11.bookings_2025_09` | 2025-09-01 — 2025-10-01 UTC | 448 064 |
| `hw11.bookings_2025_10` | 2025-10-01 — 2025-11-01 UTC | 434 159 |
| `hw11.bookings_2025_11` | 2025-11-01 — 2025-12-01 UTC | 410 670 |
| `hw11.bookings_default` | Остальные даты | 0 до теста |

Миграция выполнена командой:

```sql
INSERT INTO hw11.bookings_part (book_ref, book_date, total_amount)
SELECT book_ref, book_date, total_amount FROM bookings.bookings;
ANALYZE hw11.bookings_part;
```

Проверка с `tableoid::regclass` показала указанное выше распределение по трём месячным секциям. После тестовой транзакции общее число строк в секционированной таблице составило **1 292 893**, как и в оригинале.

## 4. Сравнение выполнения запроса до и после

Сравнивался **один и тот же логический запрос** за сентябрь 2025 года:

```sql
SELECT count(*)
FROM <таблица>
WHERE book_date >= timestamptz '2025-09-01 00:00:00+00'
  AND book_date <  timestamptz '2025-10-01 00:00:00+00';
```

Вместо `<таблица>` подставлялись `bookings.bookings` и `hw11.bookings_part`. Полные фактические выводы `EXPLAIN (ANALYZE, BUFFERS)` приведены в файле `explain_results.txt`.

| Показатель | Исходная таблица | Секционированная копия |
|---|---|---|
| План чтения | `Parallel Seq Scan on bookings` | `Parallel Seq Scan on bookings_2025_09` |
| Просмотренные секции | Нет секций, читается вся исходная таблица | Только сентябрьская секция |
| Подходящих строк | 448 064 | 448 064 |
| `Execution Time` | **56.584 ms** | **39.638 ms** |
| `Buffers: shared hit` | 352 | 2854 |
| `Buffers: shared read` | 7888 | 0 (не указан) |
| Всего общих буферов (hit + read) | 8240 | 2854 |
| Запущено worker-процессов | 2 | 1 |

**Наблюдаемый результат одного прогона:** запрос к копии был примерно в **1,43 раза быстрее** (снижение времени примерно на **30%**) и затронул меньше страниц. При этом это **не изолированный бенчмарк**: исходная таблица читалась частично с диска (`read=7888`), секция находилась в кеше (`hit=2854`), также различалось число параллельных работников. Поэтому нельзя приписывать всю разницу времени только секционированию или гарантировать аналогичный выигрыш в других условиях.

Главное объективное подтверждение пользы: **partition pruning** — план после секционирования содержит только `bookings_2025_09`, а секции октября и ноября исключены.

### Нюанс при выборе тестового диапазона

Сначала был выполнен запрос за июль 2025 года, когда данные отсутствовали. Он вернул 0 строк, но потребовал `Parallel Seq Scan` исходной таблицы и выполнялся **34.131 ms**. После проверки фактического диапазона дат тест корректно повторили за сентябрь, где есть 448 064 записей. Это не ошибка SQL — просто исходный период был вне диапазона данных.

## 5. Проверка операций INSERT / UPDATE / DELETE

Тест выполнен в одной транзакции; затем применён `ROLLBACK`, чтобы не оставлять экспериментальную запись.

1. **INSERT:** запись `book_ref='HW11ZZ'`, `book_date='2025-12-15 12:00:00+00'` с суммой `15000.00` автоматически попала в `hw11.bookings_default` (`INSERT 0 1`).
2. **UPDATE:** дата изменена на `2025-11-15 12:00:00+00`, сумма на `17500.00`. PostgreSQL переместил строку в `hw11.bookings_2025_11` (`UPDATE 1`).
3. **DELETE:** тестовая запись удалена (`DELETE 1`), запрос по `book_ref` вернул `count(*) = 0`.
4. **ROLLBACK:** тестовые изменения отменены, итоговое количество строк `hw11.bookings_part` — **1 292 893**.

Эксперимент подтвердил маршрутизацию вставки, перемещение строки при обновлении ключа секционирования и удаление через родительскую таблицу.

## 6. Итоги, ограничения и применение

- `RANGE` по `book_date` подходит для данных с временной привязкой и запросов с ограниченным диапазоном дат.
- Для запроса за сентябрь PostgreSQL исключил нерелевантные месяцы. Это может сокращать объём чтения и облегчать управление историческими данными, в том числе удаление/архивирование старых секций.
- Для запросов **без фильтра по `book_date`** секционирование само по себе не гарантирует ускорения: PostgreSQL может просматривать много секций.
- Слишком большое число секций усложняет планирование и сопровождение. Будущие месяцы желательно создавать заранее, чтобы не накапливать строки в `DEFAULT`.
- При промышленной миграции необходимо отдельно проработать уникальность `book_ref`, ссылочную целостность таблицы `tickets`, сопутствующие индексы, а также процедуру переключения приложений на новую таблицу.
- Результаты производительности основаны на однократных измерениях и зависят от кеша и параллельности. Для строгого сравнения нужно повторить испытания с одинаковым состоянием системы и несколькими прогонами.

**Вывод:** создана корректно секционированная учебная копия таблицы бронирований, перенесены все 1 292 893 строк, подтверждено исключение ненужных секций при выборе за месяц, продемонстрированы все основные операции DML. Исходная таблица не менялась.
