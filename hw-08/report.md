# HW08 — Блокировки, ожидания и взаимоблокировки PostgreSQL

**Сценарий:** «Ночная Лама» — зависания при обновлении статусов заказов, ожидания строковых блокировок и взаимоблокировки при разном порядке захвата ресурсов.  
**Среда:** Ubuntu 26.04.1 LTS (UTM), PostgreSQL **17.11**, кластер `17/main`, порт `5432`, тестовая база `hw08db`.  
**Дата эксперимента:** 04.11.2026 (временные метки журнала приведены в UTC).  
**Метод:** три независимые сессии `psql`, наблюдение через `pg_locks` / `pg_stat_activity`, диагностика по серверному журналу.

## 1. Настройка журналирования блокировок (пункт 1)

Параметры применены раздельными командами `ALTER SYSTEM`, затем выполнен `pg_ctlcluster 17 main reload`.

```sql
ALTER SYSTEM SET log_lock_waits = on;
ALTER SYSTEM SET deadlock_timeout = '200ms';
```

Проверенный результат:

```text
log_lock_waits = on
deadlock_timeout = 200ms
```

`log_lock_waits` включает сообщения о длительном ожидании; `deadlock_timeout` задаёт момент проверки на взаимоблокировку и порог сообщения об ожидании. Первоначальная попытка передать два `ALTER SYSTEM` одним вызовом `psql -c` вызвала `ALTER SYSTEM cannot run inside a transaction block`; после разделения команд настройки применены успешно.

## 2. Три сессии и ожидание одной строки (пункты 2–7)

Создана тестовая таблица:

```sql
CREATE TABLE orders (id integer PRIMARY KEY, status text NOT NULL);
INSERT INTO orders (id, status) VALUES (1, 'new');
```

Три сессии подключились к `hw08db`. Сессия 1 начала транзакцию и обновила `orders.id = 1`, не выполняя `COMMIT`; сессии 2 и 3 попытались обновить ту же строку.

| Сессия | PID | Состояние на снимке | Операция | Непосредственный блокирующий PID |
|---|---:|---|---|---:|
| `hw08_session_1` | 2636 | `idle in transaction` | `UPDATE orders ... WHERE id = 1` выполнен, транзакция открыта | нет |
| `hw08_session_2` | 2948 | `active`, `wait_event_type = Lock` | `UPDATE` той же строки ждёт завершения транзакции 1262945 | 2636 |
| `hw08_session_3` | 3258 | `active`, `wait_event_type = Lock` | `UPDATE` той же строки ждёт блокировку tuple | 2948 |

Наблюдаемая очередь: **PID 3258 → PID 2948 → PID 2636** (стрелка означает «ждёт»). Это **не** взаимоблокировка: цикла нет, после завершения транзакции 2636 очередь может продвинуться.

Снимок `pg_locks` содержал **15 строк**. Исходный скриншот: [01_pg_locks_3_sessions.png](screenshots/01_pg_locks_3_sessions.png).

### 2.1. Разбор записей `pg_locks`

| PID | `locktype` | `mode` | `granted` | Объект / значение | Что означает |
|---:|---|---|---|---|---|
| 2636 | `relation` | `RowExclusiveLock` | true | `orders` | Табличная блокировка для операции UPDATE; не блокирует всю таблицу от обычного чтения. |
| 2636 | `relation` | `RowExclusiveLock` | true | `orders_pkey` | Блокировка отношения индекса, используемого обновлением. |
| 2636 | `transactionid` | `ExclusiveLock` | true | XID 1262945 | Сессия удерживает блокировку собственного XID до завершения транзакции. |
| 2636 | `virtualxid` | `ExclusiveLock` | true | Собственный VXID | Служебная блокировка виртуального идентификатора транзакции. |
| 2948 | `transactionid` | `ShareLock` | **false** | XID 1262945 | Ожидание завершения транзакции сессии 1; `pg_blocking_pids = {2636}`. |
| 2948 | `relation` | `RowExclusiveLock` | true | `orders` | Табличная блокировка получена, несмотря на ожидание строки. |
| 2948 | `relation` | `RowExclusiveLock` | true | `orders_pkey` | Блокировка отношения индекса получена. |
| 2948 | `transactionid` | `ExclusiveLock` | true | XID 1262946 | Блокировка собственного XID. |
| 2948 | `tuple` | `ExclusiveLock` | true | Строка в `orders` | Получена блокировка кортежа, используемая для организации очереди; обновление ещё ждёт XID 1262945. |
| 2948 | `virtualxid` | `ExclusiveLock` | true | Собственный VXID | Служебная блокировка. |
| 3258 | `tuple` | `ExclusiveLock` | **false** | Строка в `orders` | Ожидает блокировку кортежа, удерживаемую сессией 2; `pg_blocking_pids = {2948}`. |
| 3258 | `relation` | `RowExclusiveLock` | true | `orders` | Табличная блокировка для UPDATE получена. |
| 3258 | `relation` | `RowExclusiveLock` | true | `orders_pkey` | Блокировка отношения индекса получена. |
| 3258 | `transactionid` | `ExclusiveLock` | true | XID 1262947 | Блокировка собственного XID. |
| 3258 | `virtualxid` | `ExclusiveLock` | true | Собственный VXID | Служебная блокировка. |

**Тонкость:** `granted = true` для `tuple` у PID 2948 не означает, что UPDATE завершился. Реальное препятствие у него — ожидание `ShareLock` на `transactionid` 1262945. Также `RowExclusiveLock` на таблице — это название режима табличной блокировки, а не подтверждение эксклюзивной блокировки каждой строки таблицы.

## 3. Взаимоблокировка трёх транзакций (пункт 8)

Для независимого захвата строк использованы `orders.id = 1, 2, 3`:

1. Сессия 1: `BEGIN; UPDATE orders SET status = 'session_1' WHERE id = 1;`
2. Сессия 2: `BEGIN; UPDATE orders SET status = 'session_2' WHERE id = 2;`
3. Сессия 3: `BEGIN; UPDATE orders SET status = 'session_3' WHERE id = 3;`

Затем каждая сессия попыталась обновить строку следующей: сессия 1 — `id = 2`, сессия 2 — `id = 3`, сессия 3 — `id = 1`.

Реальный журнал зафиксировал цикл:

| Процесс | Ожидает завершения транзакции | Блокируется процессом | Текущий SQL |
|---:|---:|---:|---|
| 3258 | 1262952 | 4733 | `UPDATE orders SET status = 'wait_1' WHERE id = 1;` |
| 4733 | 1262953 | 2948 | `UPDATE orders SET status = 'wait_2' WHERE id = 2;` |
| 2948 | 1262954 | 3258 | `UPDATE orders SET status = 'wait_3' WHERE id = 3;` |

**Цикл:** 3258 → 4733 → 2948 → 3258. PostgreSQL обнаружил его **04.11.2026 в 10:34:16.638 UTC** и выдал `ERROR: deadlock detected` у PID 3258. После прерывания его транзакции PID 2948 получил ожидаемую блокировку через 4379.904 мс. Скриншот ошибки: [02_three_session_deadlock.png](screenshots/02_three_session_deadlock.png).

### Можно ли расследовать deadlock постфактум?

**Да, в существенной степени.** Серверный журнал показывает время, PID участников, XID ожидаемых транзакций, направления зависимости и SQL-операторы, на которых возник цикл. Этого достаточно, чтобы объяснить конкретную взаимоблокировку. Но он **не гарантирует полной истории** транзакций: предыдущие запросы, параметры приложения и бизнес-контекст могут отсутствовать. Для расширенной диагностики полезны `application_name`, идентификатор заказа в прикладных логах и корреляция событий; журналировать все запросы в production нужно с учётом объёма и конфиденциальности.

## 4. Могут ли два одиночных `UPDATE` без `WHERE` взаимно заблокироваться? (пункт 9)

**Да, возможны сценарии, но отсутствие `WHERE` само по себе не создаёт deadlock.** Если обе операции обходят строки в одном порядке и не затрагивают дополнительных ресурсов, одна обычно ожидает другую. Цикл возникает, если транзакции удерживают несовместимые блокировки на разных ресурсах и запрашивают их в противоположном порядке. Источником различного порядка могут быть другие объекты, побочные действия триггеров или планы доступа.

В тесте `deadlock_star` создано 10 000 строк и индекс по `value DESC`. Для обеих сессий `EXPLAIN (COSTS OFF)` показывал **`Seq Scan on deadlock_star`**, в том числе после `SET enable_seqscan = off; SET enable_bitmapscan = off;`. Поэтому исходный вариант **не подтвердил** разные планы доступа и сам по себе не был предъявлен как воспроизведённый deadlock. Скриншоты: [03](screenshots/03_star_table_10000_rows.png), [04](screenshots/04_update_explain_session_a.png), [05](screenshots/05_update_explain_session_b.png).

## 5. ⭐ Дополнительный эксперимент: две команды `UPDATE` без `WHERE`

Для гарантированного различия порядка захвата ресурсов создана вспомогательная таблица `star_resources(id, value)` со строками 1 и 2 и `BEFORE UPDATE FOR EACH STATEMENT`-триггер `star_update_trigger` на `deadlock_star`.

- Сессия с `application_name = 'star_a'` внутри триггера сначала обновляла `star_resources.id = 1`, делала паузу `pg_sleep(2)`, затем обновляла `id = 2`.
- Сессия с `application_name = 'star_b'` обновляла те же строки в обратном порядке: 2 → пауза → 1.
- **Обе внешние команды были одинаковыми и не содержали WHERE:**

```sql
UPDATE deadlock_star SET value = value + 1;
```

**Фактическое подтверждение в журнале, 10:41:17.194 UTC:**

```text
ERROR: deadlock detected
DETAIL: Process 5353 waits for ShareLock on transaction 1262965; blocked by process 4733.
        Process 4733 waits for ShareLock on transaction 1262966; blocked by process 5353.
        Process 5353: UPDATE deadlock_star SET value = value + 1;
        Process 4733: UPDATE deadlock_star SET value = value + 1;
CONTEXT: while updating tuple (0,3) in relation "star_resources"
         SQL statement "UPDATE star_resources SET value = value + 1 WHERE id = 1"
         PL/pgSQL function star_update_trigger() line 10 at SQL statement
```

PID 4733 затем получил ожидаемую блокировку через 1684.874 мс. Фрагмент журнала также показывает действие триггера для `star_resources.id = 2` (строка 6 функции).

**Вывод со звёздочкой:** две транзакции, каждая с одной внешней командой `UPDATE` той же таблицы без `WHERE`, действительно могут вызвать deadlock **при наличии триггера, который захватывает дополнительные блокировки в противоположном порядке**. Это демонстрация возможности с побочными действиями, **а не** доказательство взаимоблокировки двух простых `UPDATE` без триггеров. В данном случае PostgreSQL сообщил о цикле и прервал одну транзакцию.

## 6. Практические выводы для «Ночной Ламы»

- Долго открытая транзакция (`idle in transaction`) может удерживать изменение заказа и вызывать очередь записей; ожидание не обязательно связано с высокой нагрузкой CPU.
- `pg_stat_activity` + `pg_locks` + `pg_blocking_pids()` позволяют определить держателя блокировки и ожидающих; ключевые строки — с `granted = false`.
- **Очередь** без цикла разрешается, когда блокирующая транзакция завершается. **Deadlock** — замкнутый цикл, для разрыва которого PostgreSQL отменяет одну из транзакций.
- В приложении следует делать транзакции короткими, захватывать `orders` и `courier_assignments` в едином порядке во всех потоках, предусматривать повтор транзакции после SQLSTATE `40P01` и не держать транзакции открытыми во время сетевых вызовов.
- Для расследования полезны серверные записи `log_lock_waits`, сообщения `deadlock detected`, PID, SQL, идентификатор бизнес-операции и `application_name`.
